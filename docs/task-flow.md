# 复杂任务流程

ActX 内置了一套面向复杂任务的多 Agent 协作机制。当用户提出的任务涉及多步骤、多依赖、跨领域知识或较高不确定性时，系统会自动将其识别为复杂任务，并交由专门的任务处理管线来拆解、调度、执行和验证，最终产出可靠的结果。

## 核心设计理念

### Agent 责任分离

复杂任务被拆解为多个子任务后，每个子任务会根据其类型分配给专门的 Agent 来处理。不同 Agent 拥有不同的系统提示、工具集和插件配置，使其在各自擅长的领域发挥最佳能力。

例如，一个涉及"开发数据看板并分析业务指标"的复杂任务，规划 Agent 会将其拆解为编码类子任务和业务分析类子任务，分别交给不同的 Agent 执行：

| Agent | 擅长领域 | 说明 |
|-------|---------|------|
| **Coding Task Worker** | 编码任务 | 擅长完成编码类任务，可在沙盒环境中编写并执行代码 |
| **General Task Worker** | 通用任务 | 可完成大多数日常任务和业务查询 |

目前系统默认配置了上述两类子任务 Agent。在实际使用中，建议用户根据自身业务需求配置更多专业领域的 Agent（如市场调研 Agent、数据分析 Agent、文档撰写 Agent 等），让规划 Agent 在拆解任务时能够将子任务分配给最合适的专业 Agent，从而获得更高质量的执行结果。

### 独立上下文

每个子任务 Agent 拥有独立的上下文空间，互不干扰。执行 Agent 的上下文中仅包含与当前子任务直接相关的信息：

- 子任务的描述和预期输出
- 输入数据（来自前置子任务的执行结果、原始任务描述等）
- 重试时的补充建议（如果该子任务是重试执行）

这种隔离设计确保每个 Agent 在决策时不会被无关信息干扰，同时也避免了长对话导致的上下文窗口溢出问题。

### 任务节点评审与重试

任务执行过程中设置了多个质量关卡：

1. **规划评审**：规划 Agent 生成的任务计划会经过规范性评审，检查任务组间的依赖关系是否合理、输入输出是否匹配。不满足要求时会进行有限重试（最多 2 次），确保任务计划在进入执行前就是正确的。
2. **子任务结果评估**：每个子任务执行完成后，调度 Agent 会对其结果进行评估。评估不合格时，调度 Agent 可以：
   - **重试**：给出改进建议，让执行 Agent 重新执行该子任务
   - **补充信息**：要求用户补充缺失的关键信息后继续
   - **继续执行**：结果合格，推进到下一组任务

### 异构模型分工

不同 Agent 可以根据任务特点配置不同的底层模型。例如：

- 评估和规划阶段使用具备强推理能力的模型（开启思维链），确保分析和拆解的准确性
- 执行阶段可以使用成本更优的模型，因为子任务通常目标明确、范围可控
- 调度 Agent 需要结构化输出能力（JSON 模式），以便精确解析评估结果和调度决策

这种异构模型分工在保障质量的同时，有效控制了整体调用成本。

## 任务流程详解

整个复杂任务的处理分为两个大阶段：**任务单创建**和**任务单执行**。

![任务流程图](/assets/任务流程.drawio.png)

### 阶段一：任务单创建

#### 1. 快速评估

用户提交任务后，主 Agent 首先进行快速判断：

- **简单任务**：如常识问答、单一计算等一眼可判断复杂度的任务，由主 Agent 直接执行并返回结果，不进入复杂任务管线
- **疑似复杂任务**：无法一眼确认复杂度的任务，进入下一步深度评估

#### 2. 复杂度评估

主 Agent 调用**评估 Agent**，从五个维度对任务进行量化分析：

| 维度 | 评分范围 | 评估内容 |
|------|---------|---------|
| 步骤与分支 | 1-5 | 任务需要多少个步骤，是否存在条件分支 |
| 依赖关系 | 1-5 | 步骤之间的前后依赖程度 |
| 知识广度 | 1-5 | 需要跨多少个领域的知识 |
| 不确定性 | 1-5 | 任务目标和路径的明确程度 |
| 执行风险 | 1-5 | 执行过程中可能遇到的风险 |

五个维度得分相加得到总分（5-25 分），并综合判定整体复杂度等级（Low / Medium / High）以及是否需要规划。

- **复杂度较低**：由主 Agent 直接执行
- **复杂度较高**：进入任务规划阶段

#### 3. 任务规划

**规划 Agent** 接收用户任务描述和评估结果，将任务拆解为结构化的任务计划：

- **任务组（Task Group）**：按逻辑相关性将子任务分组，组内子任务可并行执行，组间按依赖关系串行推进
- **子任务（Sub Task）**：每个子任务包含明确的描述、预期输出、输入依赖（来自哪些子任务或任务组的结果）以及分配的 Agent

规划完成后，系统会对任务计划进行**规范性评审**，验证：

- 任务组之间的依赖关系是否构成有向无环图（DAG），避免循环依赖
- 每个子任务的输入是否都能从已定义的输出中获取
- 任务计划的整体结构是否完整、可执行

如果评审不通过，系统会携带失败原因重新调用规划 Agent 进行修正，最多重试 2 次。评审通过后，**任务单创建完成**。

### 阶段二：任务单执行

任务单创建完成后，**任务调度器**接管整个执行流程。

#### 1. 任务编排

调度器根据任务计划中的依赖关系，将所有子任务编排为可执行的批次。同一任务组内的子任务如果没有相互依赖，会被安排在同一批次中**并行执行**，以提高效率。

#### 2. 取出下一组任务

调度器按照编排顺序，依次取出下一组待执行的子任务。

#### 3. 子任务执行

每个子任务被分配给对应的**执行 Agent**。执行 Agent 的上下文中仅包含：

- 子任务的描述和预期输出
- 输入数据（来自前置子任务的执行结果、原始任务描述等）
- 重试时的补充建议（如果该子任务是重试执行）

执行 Agent 专注于完成当前子任务，不感知全局任务状态。

#### 4. 结果评估

子任务执行完成后，**调度 Agent** 对结果进行评估：

- **评估通过**：记录子任务结果，检查是否所有任务组都已完成
  - 全部完成 → 进入执行结果总结
  - 未完成 → 继续执行下一组任务
- **执行结果不合格**：进入异常处理流程

#### 5. 异常处理

当子任务执行结果不合格时，调度 Agent 进行判断：

- **需要重试**（未达到最大重试次数）：调度 Agent 分析失败原因，生成改进建议，将子任务重新放入执行队列。执行 Agent 重试时会收到历史执行记录和改进建议，有针对性地修正
- **需要补充信息**：任务因缺少关键信息无法继续，调度器会要求用户补充信息。用户补充后，任务从断点处继续执行
- **达到重试次数上限**：任务执行失败，调度器总结失败原因后返回，由主 Agent 将失败信息以清晰易懂的方式告知用户，并询问后续处理方式（重试、调整需求等）

#### 6. 执行结果总结

所有任务组执行完成后，主 Agent 对各子任务的执行结果进行汇总和整合：

- 梳理各子任务的核心产出
- 以清晰的结构呈现给用户
- 必要时附上简要说明或后续建议

至此，整个复杂任务处理流程结束。
