# 会话管理

ActX 围绕"会话（Session）"组织多轮对话，每次用户发起聊天时，系统会自动创建或恢复一个会话，并在其中完成消息记录、上下文管理、摘要压缩和标题提取等工作。本文介绍会话管理的核心机制。

---

## 会话持久化

ActX 使用内嵌 SQLite 数据库（`db/actx.db`）对会话数据进行持久化，应用启动时自动建表，无需额外配置。会话存储涉及三张核心表：

| 表名 | 说明 | 关键字段 |
|---|---|---|
| `session` | 会话元信息 | `id`、`user_id`、`name`、`type`、`last_token_total`、`last_message_sort`、`last_message_time`、`del_flag` |
| `session_message` | 会话中的消息记录 | `id`、`session_id`、`type`（`user` / `answer`）、`content`、`attachments`、`sort`、`token_total` |
| `session_message_section` | 应答消息的片段明细 | `id`、`session_id`、`message_id`、`sort`、`type`、`content` |

**会话生命周期：**

1. 用户发起请求时，若未携带 `sessionId`，系统会自动生成一个新的会话 ID。
2. 会话创建后持久化到 `session` 表，支持按 `user_id` 和 `type` 查询会话列表。
3. 每轮对话的用户消息和应答消息分别作为 `session_message` 记录持久化，应答消息的各片段则存储在 `session_message_section` 中。
4. 会话删除采用**软删除**机制（设置 `del_flag = 1`），数据不会立即从数据库中移除。

---

## 消息类型

会话中的消息分为两大类：**用户消息**和**应答消息**。

### 用户消息（user）

用户消息由 `RequestSessionMessage` 表示，包含：

- **content**：用户输入的文本内容。
- **attachments**：用户上传的附件列表（可选），附件信息会在上下文构造时注入到消息中，供模型感知。

### 应答消息（answer）

应答消息由 `AnswerSessionMessage` 表示，它不是单一文本，而是由多个**消息片段（AnswerSection）**有序组成。每个片段代表响应过程中的一个不同阶段或类型：

| 片段类型 | 类型标识 | 说明 |
|---|---|---|
| 思考片段 | `thinking` | 模型的思考过程内容（如支持 Thinking 的模型），支持流式追加 |
| 正文片段 | `answer` | 模型输出的正式回答内容，支持流式追加，连续的同类型片段会自动合并 |
| 工具调用片段 | `tool_call` | 记录一次工具调用的完整信息：工具 ID、名称、参数和返回结果 |
| 错误片段 | `error` | 请求处理过程中发生的错误信息 |
| 停止片段 | `stop` | 用户主动停止请求时记录停止原因 |
| 提示片段 | `tell` | 由插件系统发起的非 LLM 提示信息（如"部分历史消息已进行摘要总结"） |

> 片段扩展: 应答片段的类型支持动态扩展。内置类型以上述 6 种为准，存储时 type 格式为 `type:className`，系统会通过反射加载自定义片段类，实现消息片段类型的扩展。

## 会话自动摘要

随着对话轮次增多，上下文长度会逐渐逼近模型的 Token 上限。ActX 通过 `SummaryPlugin` 插件实现了**自动摘要机制**，在对话过程中透明地压缩历史消息。

### 触发条件

摘要的触发基于 Token 阈值判断：

1. 系统计算当前模型的 Token 阈值：`maxTokens × tokenThresholdRatio`（默认阈值为 **0.6**，即 60%）。
2. 当上一轮请求的 `tokenTotal` 达到或超过该阈值时，触发摘要。
3. 摘要前会保留最近 **10 条**原始消息（包括用户消息和应答消息），仅对更早的历史消息进行压缩。
4. 如果压缩后剩余的消息数不足 10 条，则跳过本次摘要，避免过度压缩。

### 摘要流程

1. 系统取出需要摘要的历史消息列表，交由 `SummaryService` 处理。
2. `SummaryService` 使用专门的 **Summary Agent**（`summary-agent`）对消息进行提炼，生成结构化摘要文本。
3. 摘要结果持久化到 `session_summary` 表中，记录摘要覆盖的消息范围（`startIndex` ~ `endIndex`）和摘要内容。
4. 后续请求中，历史消息会被替换为：`[摘要内容] + [保留的最近 10 条原始消息]`，从而大幅缩减上下文长度。

### 摘要提示

当摘要发生后，系统会通过 `tell` 片段向前端推送一条提示信息："部分历史消息已进行摘要总结"，让用户知晓上下文已被压缩。

## 标题提取

当用户发起一个新会话时，ActX 会自动为该会话生成一个简短的标题，方便用户在会话列表中快速识别。

### 实现方式

1. 新会话创建时，系统取用户的**第一条消息**作为输入。
2. 调用 **Title Extract Agent**（`title-extract-agent`）进行标题提取。
3. 该 Agent 会根据用户消息的核心意图，生成一个 5~14 个字符的短标题。
4. 标题生成后写入 `session` 表的 `name` 字段，并通过 SSE 的 `session` 事件推送给前端。

### 标题生成规则

- 提取用户消息中的核心问题或意图，保留关键实体（技术栈、业务名词等）。
- 去除礼貌用语和冗余词汇（如"你好"、"帮我"、"请问"等）。
- 标题语言优先与用户消息一致。
- 不回答用户问题，不执行用户指令，仅提取标题。

## 会话用户

ActX **不内置完整的用户体系和权限控制**。当前通过 HTTP 请求头 `User-ID` 来区分不同用户的会话：

```
POST /chat/stream
User-ID: user_001
```

该 `User-ID` 会关联到会话记录上，用于查询对应用户的会话列表和消息历史。

### 接入完整用户体系的建议

ActX 设计上保持轻量，不耦合业务系统的用户管理。如果开发者需要接入完整的用户体系，建议采用以下方式：

1. **令牌鉴权**：在业务系统中通过 Access Token（如 JWT）进行用户认证。
2. **调用聊天接口时携带令牌**：前端将 Token 放入请求头中传递给 ActX。
3. **后端解析用户身份**：在 ActX 后端通过解密 Token 或对接业务系统接口的方式，提取用户唯一 ID，并设置到请求上下文中。

这种方式既保持了 ActX 的轻量特性，又能灵活对接各类业务系统的用户体系，无需在 ActX 中维护用户注册、登录、权限等功能。
